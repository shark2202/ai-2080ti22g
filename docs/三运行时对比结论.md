## 二、四条结论

### 1. 27B 的唯一"通用"解仍是 llama.cpp

只有它能读通用 GGUF、只吃 13 GB、还给出 256K logical 上下文。NInfer 同样能跑 27B，但代价是
**18.2 GB 专有权重 + 4.4 GiB 主机内存 + 13 条依赖坑**，而且**权重不能复用**
（Saluki、Q2-LynnStyle 全部用不上 —— `.ninfer` 没有 GGUF reader）。

### 2. NInfer 是货真价实的第二选择

它的官方标准测量协议在本机复现到 **0.8–4.9%**，**MTP 接受率 0.3771 vs 官方 0.377（四位小数一致）**，
真文本场景 +1.7~2.1%。**并发**（同口径、同题面去重）：4 路聚合 **91.8 tok/s**，每路 ±6%，
每路带 16K 上下文 —— 27B 的并发高于 vLLM 9B FP8 的 74.8/85.3，但**低于同口径下 llama.cpp 的 124.9**。
它的强项是**每路更齐**（±6% vs llama.cpp 的 ±11%）与**每路 2 倍上下文**。

> ⚠️ **两次修订**：
> 1. 早期版本把"并发"划归 vLLM 专属。**该判断已过时** —— NInfer 27B 四路聚合 91.8 tok/s 已高于
>    vLLM 9B FP8 的 74.8/85.3。vLLM 相对这两个 27B 引擎只剩两个优势：**上下文长度**
>    （9B 262K vs NInfer 27B 152K）与**模型可换性**（vLLM 能跑 2B/4B/9B，NInfer 只认 `.ninfer` 权重）。
> 2. 但**同口径下 llama.cpp 的 27B 是 124.9，比 NInfer 的 91.8 更高** —— 之前那份"NInfer 并发最好"
>    的判断缺了 llama.cpp 对照，且两边都用同一个 prompt，被 llama.cpp 的 `ngram-mod` 缓存命中污染
>    （接受长度从 3–6 虚高到 18–53）。修正过程见 `runtime-research.zh-CN.md` §5.4.1b。

### 3. vLLM 在这台机上该做的是"小模型 + 超长上下文"，不是 27B

27B 的 GGUF 路径是**架构级阻塞**：`vllm-gguf-plugin` 支持的 K/IQ 类型很广（"K-quant 不被支持"是过时说法），
缺的是 `qwen3_5` / `hybrid` / `gdn` / `linear_attention` / `mamba` 的实现 → **任何 Qwen3.8 GGUF 都载不进来**，
哪怕 5.71 GB 的 IQ1_S。safetensors 路径地板 18.60 GB → KV 余量 ≈ 0。
9B FP8 是它的主场：prefill 3,020 tok/s、262K、4 路 85.3。

### 4. 投机解码的收益由输出熵决定，不由引擎决定

两个独立引擎、两种投机方案，同一结论：

| 输出类型 | llama.cpp DFlash2 | NInfer MTP d3 |
|---|---|---|
| 结构化 JSON / tool call | 0.75–0.92（正收益） | **97.2%（1.99×）** |
| 代码 | — | 70.7%（1.58×） |
| 中文散文 | **0.12（负收益）** | 48.8%（1.25×） |
| 中文对话 | — | **33.2%** |

→ **agent / 代码 / 工具调用：开投机。自由创作：别开。**
NInfer 官方文档也独立说过"散文 depth 1–2 更好、代码 depth 3 最好"（本机实测：散文 d1 接受率 69.9% vs d3 的 48.8%）。

## 三、选型建议（本机）

| 需求 | 选 | 理由 |
|---|---|---|
| 27B 日常对话 / 写剧本 | **llama.cpp**（按内容决定是否开投机） | 256K logical、13 GB、权重通用；创作负载下投机要关 |
| 27B + agent / 代码 / 工具调用 | **NInfer**（MTP d3） | 48.5–53.0 tok/s；并发每路更齐（±6%），4 路聚合 91.8（llama.cpp 同口径 124.9），每路 24.5K 上下文 |
| 27B + 要换模型 / 换量化 | **llama.cpp** | 唯一能换 GGUF 的 |
| 9B + 超长上下文 + 高并发 | **vLLM** | 262K、prefill 3,020、4 路 85.3 |
| 显存要省 | **llama.cpp + Saluki IQ2-mix** | 8,928 MiB（无投机）/ 11,510（+DFlash2），比现役 27B 省 4.2 GiB |
| GPU 被 ComfyUI 占 | **vLLM 9B**（GPU_UTIL 0.78 → 133K） | 唯一为"共存"设计过的 |

## 四、三个必须记住的限制

1. **三者不能同时驻留**：13.9 + 18.3 + 18.1 ≫ 22.5 GB。
   且 `start-llama.sh` 按二进制路径杀同款进程 —— **两个 llama.cpp 服务不能先后用同一脚本起**
   （端口分开只避免撞端口，不解决互杀）。
2. **NInfer 的性能可跨平台引用，输出不可**：同权重同语料，perplexity overall
   **4.3432 vs 官方 4.7968（−9.5%）**。已排除权重漂移（artifact 自 2026-09-15 未变、sha256 一致）
   与语料漂移（`eval/corpora/perplexity-1m/data` 停在 2026-08-29）→ **两个构建浮点数值不等价**
   （Windows/MSVC/CUDA 12.9 vs Linux/gcc/CUDA 13.4；Turing 无 bf16 张量核，累加顺序随编译器而变）。
   **在 Turing 上评估模型质量，别拿 PPL 对官方数字。**
3. **NInfer 吃 4.4 GiB 主机内存**（pinned）。本机 `Committed_AS` 曾超 `CommitLimit` 2.6 GiB ——
   内存紧张时它回退 device residency（多占 1.26 GiB 显存）。
4. **NInfer 在并发 + prefix 复用下会整个崩掉**（引擎级失败、不自恢复、必须重启进程）。
   本机的解法是加 `--no-prefix-reuse`，而这在本机**不亏**（checkpoint 物化比重新 prefill 还慢，
   串行同 prompt 从 9.4 提到 17.6 tok/s）。详见 `runtime-research.zh-CN.md` §5.4.1c。
