# 行业标准基准测评指南（lm-evaluation-harness）

本文件说明如何用**行业事实标准**测评被测模型，产出可对外比较的分数。

---

## 一、为什么要换标准

`model-eval` 的 180 题是自建题库，**分数不可与任何公开榜单比较**。若需要"这个模型在 MMLU 上多少分"这种可对外引用的数字，必须用公开基准 + 公认框架。

社区事实标准由两部分构成：

| 组成 | 说明 |
| --- | --- |
| **公开基准数据集** | MMLU / MMLU-Pro / C-Eval / CMMLU / GSM8K / HumanEval / EvalPlus / IFEval / ARC-Challenge / LiveCodeBench |
| **测评框架** | **EleutherAI lm-evaluation-harness**（GitHub 40k+ star，事实标准），配套 `guidance`、`lighteval`、`OpenCompass` 等 |

**本项目采用 lm-evaluation-harness**：它对 llama.cpp 有官方支持（`gguf` 后端），且任务数量最多、社区维护最活跃。

## 二、两条路线，先选一条

### 路线 A：在 2080Ti 设备上跑（推荐）

模型和测评在同一台机器，不受网络影响；Linux 环境干净，装包顺利。

```bash
ssh user@100.69.133.37

# 1. 建独立 venv（不要污染系统 Python）
python3 -m venv ~/venvs/lmeval
source ~/venvs/lmeval/bin/activate
pip install -U pip

# 2. 安装（torch 只需 CPU 版，因为我们只调HTTP 接口，不在本地推理）
pip install lm_eval
# 若需指定 torch 版本（CPU 版体积小很多）：
# pip install torch --index-url https://download.pytorch.org/whl/cpu
# pip install lm_eval

# 3. 拉取本工具（或直接 scp 过去）
cd ~
git clone https://github.com/shark2202/ai-2080ti22g.git
cd ai-2080ti22g/model-eval

# 4. 跑标准基准
bash scripts/run_lm_eval_baseline.sh http://127.0.0.1:8080
```

### 路线 B：在测评机上跑（本机）

```bash
python3 -m venv ~/.venvs/lmeval
~/.venvs/lmeval/bin/pip install -U pip
~/.venvs/lmeval/bin/pip install lm_eval

cd model-eval
LM_EVAL_BIN=~/.venvs/lmeval/bin/lm_eval \
  bash scripts/run_lm_eval_baseline.sh http://100.69.133.37:8080
```

**注意**：`lm_eval` 依赖很重（torch / datasets / evaluate / rouge-score），磁盘和时间成本都不小。

> **本机（macOS + WorkBuddy 环境）实测：装不上。**
> 报错形如 `OSError: EEXIST: file already exists, mkdir .../pip-install-xxx/rouge-score_xxx`。
> 根因不是 pip 版本或磁盘空间，而是运行环境的沙箱拦截层拒绝创建带连字符（`-`）的目录，
> 导致任何名称含连字符的包都无法安装。换`TMPDIR`、降级 pip、`--no-build-isolation`、
> 先 `pip download` 再本地安装均无效。
> **因此本项目场景请一律走路线 A（在 2080Ti 上安装并测评）。**

## 三、任务档位

脚本用 `PROFILE` 环境变量选择任务组：

| 档位 | 任务 | 说明 |
| --- | --- | --- |
| `quick` | gsm8k, mmlu | 只验证链路通不通，最快 |
| `core`（默认） | mmlu, ceval-valid, gsm8k, humaneval | 国内外最常引用的四项，日常发版前跑这个 |
| `full` | core + mmlu_pro, ifeval, arc_challenge | 更全面，耗时显著增加 |

```bash
PROFILE=quick bash scripts/run_lm_eval_baseline.sh http://IP:8080   # 先验证链路
PROFILE=core  bash scripts/run_lm_eval_baseline.sh http://IP:8080   # 正式出分
PROFILE=full  bash scripts/run_lm_eval_baseline.sh http://IP:8080   # 全面评测
```

自定义任务：`TASKS=mmlu,arc_challenge,gpt4latin_arc bash scripts/run_lm_eval_baseline.sh ...`

## 四、任务与指标对照

| 任务 | 测什么 | 主要指标 | 后端要求 |
| --- | --- | --- | --- |
| `mmlu` | 英文通识（57 学科） | acc / acc_norm | loglikelihood（gguf 可） |
| `mmlu_pro` | 英文高难通识（10 选 1） | acc | loglikelihood（gguf 可） |
| `ceval-valid` | 中文知识（52 学科） | acc / acc_norm | loglikelihood（gguf 可） |
| `gsm8k` | 小学应用题（CoT） | exact_match | loglikelihood（gguf 可） |
| `humaneval` | Python 代码生成 | pass@1 | loglikelihood（gguf 可） |
| `ifeval` | 指令遵循（可验证） | prompt / 严格准确率 | **generate_until**，须用 `local-chat-completions` |
| `arc_challenge` | 英文科学推理 | acc / acc_norm | loglikelihood（gguf 可） |

脚本已处理这个差异：若任务表里含 `ifeval`，跑完 loglikelihood 类任务后会**自动用 chat 后端补跑**，无需手工干预。

**限制（官方明确）**：
- `gguf` 后端**不支持 `loglikelihood_rolling`**，因此 perplexity 类任务（`wikitext` 等）无法运行
- `gguf` 后端需 llama.cpp **≥ 2024-12**（依赖 `logprobs.content` 格式；旧版 `token_logprobs` 不支持）
- OpenAI ChatCompletions 类后端（含 `local-chat-completions`）**只支持 `generate_until`，不支持 logprobs**，所以只能跑生成类任务
- 首次运行需联网从 HuggingFace 下载数据集；内网服务器可设 `HF_ENDPOINT=https://hf-mirror.com` 走镜像

### gguf 后端的工作方式（官方实现说明）

不是简单地"请求 logprobs"，而是**精确的教师强制**：

1. 通过 `/tokenize` 端点分别编码 context 与 continuation
2. 用 token id 作为 prompt，配合 `logit_bias` 强制服务端采样到该 token
3. 读取该 token 的 pre-sampling logprob 与无偏 `top_logprobs`

官方称结果与 HF 后端的差异**在量化噪声范围内**。

> 注意：不能用 GBNF 语法约束来强制 continuation——语法约束解码可能选出碎片化的 token 化，
> 其 logprob 不是自然 token 化的 loglikelihood，会系统性压低分数。官方明确说明了这一点。

## 五、后端选择与参数格式（已按官方文档核实）

两个后端的 `base_url` 格式**不同**，写错会直接连不上：

### `gguf`（默认，推荐）

```bash
lm_eval --model gguf --model_args base_url=http://127.0.0.1:8080 --tasks hellaswag
```

- `base_url` **不带 `/v1`**，后端自己拼接 `/v1/completions`
- 走 **completions** 而非 chat/completions
- 支持 `generate_until` + `loglikelihood`（MMLU/C-Eval/GSM8K/HumanEval 都需要 loglikelihood）
- 若 llama-server 跑在 router 模式（多模型），追加 `model=<别名>`
- 并发度默认从 `/props` 的 `total_slots` 自动探测，可用 `parallel=N` 覆盖
- ⚠️ 不支持 `loglikelihood_rolling`（即 perplexity 类任务）

### `local-completions`（备用）

```bash
lm_eval --model local-completions \
  --model_args model=<别名>,base_url=http://127.0.0.1:8080/v1/completions \
  --tasks hellaswag
```

- `base_url` 必须是**到 `/v1/completions` 的完整路径**
- 必须显式传 `model`

### `local-chat-completions`（仅生成类任务）

```bash
lm_eval --model local-chat-completions \
  --model_args model=<别名>,base_url=http://127.0.0.1:8080/v1/chat/completions \
  --tasks ifeval --apply_chat_template
```

- 只支持 `generate_until`（**不支持 logprobs**），因此只能跑生成类任务
- 脚本在任务含 `ifeval` 时会自动调用这个后端

## 六、结果解读（重要）

跑出分数后，请连同以下四点一起陈述，否则结论会被误用：

### 1. 被测权重的真实身份

本次被测的是 `Qwen3.8-27B-EfficientThink-SimPO-Q2-LynnStyle.gguf` —— **第三方 SimPO 微调 + Q2 量化**，不是 Qwen 官方原版发布权重。任何对外材料都必须写完整权重名。

### 2. 量化会压低分数

Q2 量化是激进的压缩档位。相比官方 BF16 原版，公开基准分数通常会有明显差距。**这不是模型"能力差"，是量化损失**。要区分"模型不行"和"量化掉了太多"，需对比不同量化的分数。

### 3. 数据污染

MMLU / GSM8K / HumanEval 等公开基准的题目**大概率已进入模型的训练语料**。这意味着分数偏高，不代表真实泛化能力。这也是社区不断推出新基准（MMLU-Pro、LiveCodeBench）的原因。

### 4. 后端差异

同一权重在 llama.cpp 与 vLLM 上跑同一基准，分数可能不同（采样实现、prompt 模板、数值精度）。跨框架比较时须注明后端。

## 七、与自建题库的关系

两套并行，各有明确用途：

| | model-eval（自建 180 题） | lm-evaluation-harness（公开基准） |
| --- | --- | --- |
| 能否对外比较 | **不能** | **能** |
| 依赖 | 零第三方依赖 | 需torch/datasets 等 |
| 典型耗时 | 分钟级 | 十分钟到数小时 |
| 用途 | 日常改动回归、A/B 对比 | 发版/汇报的标准分数 |
| 数据集版本 | 报告含 SHA256，可追溯 | 由harness 锁定版本 |

**建议节奏**：日常开发用 model-eval 快速回归（改配置、换量化、开关思考模式各跑一次对比）；要出对外材料时跑 harness 出标准分。

## 八、常见问题排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `lm_eval: command not found` | 未安装或不在 PATH | 用 `LM_EVAL_BIN` 指定绝对路径 |
| 所有任务报 502 / timeout | 端点不可达 | 先跑 `python3 run_eval.py --check-endpoint` 确认服务 |
| 部分任务报 logprob 相关错误 | llama.cpp 版本过旧 | 升级 llama.cpp 至2024-12+ |
| 数据集下载失败 | 服务器在内网 / 无 HF 访问 | 预设 `HF_ENDPOINT=https://hf-mirror.com` 或提前灌缓存 |
| 分数明显低于 model card | 量化损失 + 思考模式差异 | 属正常；用 `enable_thinking` / 换量化做A/B |
| wikitext 等任务不存在 | gguf 后端不支持 perplexity | 换后端或换任务 |
